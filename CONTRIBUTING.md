# Contributing to Perch

This guide is the canonical policy for commit and pull-request writing,
public-content hygiene, and releases.

Before changing or reviewing code, read the
[code conventions](docs/code-conventions.md) for coding rules and their
verification coverage.

## Local setup

Perch uses tracked Git hooks for its fast source invariant and commit-message
checks. Activate them once after cloning:

```sh
make hooks
```

This installs the pinned development-only commit linter. It requires Node.js
22.12 or newer. Before opening a pull request, run the complete local gate:

```sh
make verify
```

## Commit messages

Every authored commit follows [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/):

```text
<type>[optional scope][!]: <description>
```

Allowed types are `build`, `chore`, `ci`, `docs`, `feat`, `fix`, `perf`,
`refactor`, `revert`, `style`, and `test`. Keep the complete header at or below
50 characters and write the description as a concise imperative.

Examples:

```text
fix(codex): preserve quota snapshot
ci: test supported macOS releases
feat!: remove legacy hook format
```

Use a body when the reason is not obvious. Put breaking-change and co-author
trailers after a blank line. True merge commits are exempt because their
messages are generated by the merge workflow; every non-merge commit
introduced by a pull request is checked in CI.

For Codex-authored commits, end the message with the exact trailer after a
blank line:

```text
Co-authored-by: Codex <noreply@openai.com>
```

Preserve legitimate existing co-authors. Attribution is required public
metadata, not private-content leakage.

## Pull requests

Resolve the actual base and head revisions before describing or validating a
pull request. Review the complete `base..head` introduced commit range and the
corresponding final diff, not only `HEAD`, the branch name, or a stale plan.
The existing range checker is:

```sh
scripts/check-commits.sh range <base> <head>
```

There is no repository pull-request template. Lead with the concrete problem
and resulting behavior, then report relevant validation and material
limitations. Distinguish checks that passed, checks that failed, and checks not
run. Rewrite the title and description if the final diff changes scope.

Include `Generated with Codex.` exactly once in a Codex-authored pull-request
body. Do not invent authors, reviewers, identities, or validation results.
Omit process narrative and conversation context from commit and pull-request
text.

## Public-content hygiene

Perch is public. Before a commit, pull request, push, or release, inspect the
actual outgoing scope: filenames and staged or final diffs, every introduced
commit, commit and pull-request text, and the contents and metadata of artifacts
that will be published.

- Do not publish credentials, private keys, tokens, cookies, private links,
  personal correspondence, customer or account data, internal documents, or
  proprietary text.
- Do not publish private prompts, agent transcripts, tool logs, internal
  deliberation, abandoned private plans, or provenance unrelated to the public
  change. `PLAN.md` and other private planning material must not be committed.
- Do not publish developer usernames, hostnames, absolute personal paths,
  device identifiers, or incidental machine- or session-derived measurements.
  In commit and pull-request prose, describe behavior generically instead of
  including real worktree or token counts, disk sizes, timings, or local paths.
- Use synthetic examples, reserved example domains, and repository-relative or
  placeholder paths. Preserve deliberately public project facts, links,
  required attribution, and purposeful validation results.
- Report a finding without reproducing the sensitive value. A clean final tree
  does not remove a secret from an earlier outgoing commit, and an ignore rule
  does not prove that a tracked file or artifact is safe.

Inspect release files themselves, not only the workflow that creates them. If an
artifact or history range cannot be inspected, report that gap; do not call it
clean. Fixing published history, rotating credentials, pushing, and publishing
all require separate authorization.

## Policy checks and manual gaps

- The tracked commit-message hook uses `scripts/check-commits.sh` to check one
  authored message. Both CI paths use its range mode to check every introduced
  non-merge commit. Commitlint enforces Conventional Commit structure,
  configured types, and the 50-character full-header limit; the range wrapper
  implements the true-merge exemption.
- `make commitlint-test` exercises accepted messages, overlong headers,
  merge-shaped authored messages, real merge commits, and range handling.
- Imperative wording, truthful scope and validation, Codex attribution, pull-
  request text, and all public-content hygiene rules require manual review.
  There is no configured secret scanner or semantic publication checker.
- `make fitness`, the selftest, and the metamorphic oracle verify product code;
  they do not validate public prose or artifact contents.

## Releases

Pushing a `v*` tag builds, tests, and attests the DMG in CI, then creates a
draft GitHub release. Before publishing it, the maintainer must:

1. Download the CI-built DMG and checksum from the draft release.
2. Verify the checksum and GitHub build-provenance attestation.
3. Hardware-sign only the verified checksum with the maintainer GPG key.
4. Verify and upload the resulting `.sha256.asc` file.
5. Confirm all three files are present, then publish the draft.

Do not rebuild or re-sign the DMG locally. The workflow refuses to overwrite an
existing release. Delete an unpublished draft before retrying its workflow;
never replace the artifacts of a published release.
