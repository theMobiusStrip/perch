# Contributing to Perch

## Local setup

Perch uses tracked Git hooks for its fast source invariant and commit-message
checks. Activate them once after cloning:

```sh
make hooks
```

This installs the pinned development-only commit linter. It requires Node.js
22.12 or newer. Before opening a pull request, run the complete local gate:

```sh
make verify
```

## Commit messages

Every authored commit follows [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/):

```text
<type>[optional scope][!]: <description>
```

Allowed types are `build`, `chore`, `ci`, `docs`, `feat`, `fix`, `perf`,
`refactor`, `revert`, `style`, and `test`. Keep the complete header at or below
50 characters and write the description as a concise imperative.

Examples:

```text
fix(codex): preserve quota snapshot
ci: test supported macOS releases
feat!: remove legacy hook format
```

Use a body when the reason is not obvious. Put breaking-change and co-author
trailers after a blank line. True merge commits are exempt because their
messages are generated by the merge workflow; every non-merge commit
introduced by a pull request is checked in CI.

## Releases

Pushing a `v*` tag builds, tests, and attests the DMG in CI, then creates a
draft GitHub release. Before publishing it, the maintainer must:

1. Download the CI-built DMG and checksum from the draft release.
2. Verify the checksum and GitHub build-provenance attestation.
3. Hardware-sign only the verified checksum with the maintainer GPG key.
4. Verify and upload the resulting `.sha256.asc` file.
5. Confirm all three files are present, then publish the draft.

Do not rebuild or re-sign the DMG locally. The workflow refuses to overwrite an
existing release. Delete an unpublished draft before retrying its workflow;
never replace the artifacts of a published release.
